# ⚡ Navix Execution Engine Mechanics

This document provides a deep technical dive into the Navix workflow execution engine, covering DAG topological sorting, runtime variable interpolation, Trigger.dev durable task orchestration, and the real-time telemetry streaming pipeline.

---

## 1. Topological Sorting & DAG Resolution

Navix represents workflows as **Directed Acyclic Graphs (DAGs)**, where nodes represent discrete tasks and edges define execution dependency order.

### Pre-Execution Graph Validation (`features/workflows/lib/validate-graph.ts`)

Before any graph can be executed or saved for a run, it must satisfy structural constraints:

```typescript
export function validateGraph({ nodes, edges }: WorkflowGraph): string[] {
  const problems: string[] = []

  // 1. Single Entry Point Rule
  const triggers = nodes.filter((n) => n.data.kind === "trigger").length
  if (triggers !== 1) {
    problems.push(`A workflow needs exactly one Start trigger (found ${triggers}).`)
  }

  // 2. Connectivity Rule
  if (edges.length === 0) {
    problems.push("Connect your nodes before running.")
  } else {
    try {
      // 3. Cycle Detection: toposort throws if a loop exists
      toposort(edges.map((e) => [e.source, e.target]))
    } catch {
      problems.push("Workflow has a cycle — remove the loop before running.")
    }
  }

  return problems
}
```

### Connected Component Filtering & Topological Ordering

In `features/workflows/tasks/run-workflow.ts`, the runner handles graphs that may contain unattached "scratchpad" nodes dropped onto the canvas:

```typescript
// 1. Collect only nodes that touch at least one edge:
const connected = new Set(edges.flatMap((e) => [e.source, e.target]))

// 2. Compute the topological execution order:
const order = toposort
  .array(
    nodes.map((n) => n.id),
    edges.map((e) => [e.source, e.target])
  )
  .filter((id) => connected.has(id))
```

- **Disconnected Nodes**: Any node not connected to an incoming or outgoing edge is excluded from execution.
- **Topological Guarantee**: If node $B$ depends on node $A$ (edge $A \rightarrow B$), node $A$ is guaranteed to execute and produce its outputs before node $B$ begins.

## 2. Dynamic Variable Interpolation Engine

The interpolation engine (`features/workflows/lib/interpolate.ts`) allows downstream nodes to read outputs generated by upstream ancestors using `{{ nodeId.path }}` placeholder tokens.

### Token Syntax & Grammar

```
{{ <nodeId>.<path> }}
```

- `<nodeId>`: The unique UUID string of the source node that produced the output.
- `<path>`: Dot-delimited or bracket-indexed path into the output object (e.g., `url`, `extraction`, `matches[0].selector`).

### Interpolation Algorithm

```typescript
export type NodeOutputs = Record<string, unknown>

const PLACEHOLDER = /\{\{\s*([^}]+?)\s*\}\}/g

function getByPath(root: NodeOutputs, path: string): unknown {
  const keys = path
    .replace(/\[(\w+)\]/g, ".$1") // Normalize items[0] -> items.0
    .split(".")
    .filter(Boolean)

  return keys.reduce<unknown>((acc, key) => {
    if (acc == null || typeof acc !== "object") return undefined
    return (acc as Record<string, unknown>)[key]
  }, root)
}

export function interpolate({
  text,
  outputs,
}: {
  text: string
  outputs: NodeOutputs
}): string {
  return text.replace(PLACEHOLDER, (_match, expr: string) => {
    const value = getByPath(outputs, expr.trim())
    if (value == null) return ""
    if (typeof value === "object") return JSON.stringify(value)
    return String(value)
  })
}
```

### Key Behaviors:
1. **Missing Data**: Resolving an unknown path returns `""` (empty string) rather than throwing an uncaught exception.
2. **Complex Objects**: If the target value is an object or array, it is safely serialized using `JSON.stringify(value)`.
3. **Ancestor Search (`useUpstreamConnections`)**: In the UI, the inspector provides clickable chips for available upstream tokens. The hook performs a breadth-first search traversing incoming edges to collect all upstream ancestor outputs.

## 3. Trigger.dev Durable Task Execution

Navix uses **Trigger.dev v4** tasks to overcome the limitations of standard serverless functions (which have strict execution time limits of 15s–60s).

### Task Configuration (`trigger.config.ts`)

```typescript
export default defineConfig({
  project: "proj_dlpllaeeqcnzecwehmzk",
  runtime: "node",
  logLevel: "log",
  maxDuration: 3600, // 1 hour max compute time per workflow
  retries: {
    enabledInDev: true,
    default: {
      maxAttempts: 3,
      minTimeoutInMs: 1000,
      maxTimeoutInMs: 10000,
      factor: 2,
      randomize: true,
    },
  },
  dirs: ["features"],
})
```

### Real-Time Lifecycle States

During execution, each step transitions through a state machine:

```
[ pending ] ──► [ running ] ──┬──► [ done ]
                              │
                              └──► [ failed ]
```

```typescript
// 1. Initial State Seeding
const steps: RunStep[] = order.map((nodeId) => ({
  nodeId,
  type: byId.get(nodeId)!.data.type,
  title: byId.get(nodeId)!.data.title,
  status: "pending",
}))
metadata.set("steps", steps)

// 2. Transition to "running"
step.status = "running"
metadata.set("steps", steps)
await metadata.flush() // Force immediate broadcast

// 3. Execution & Duration Timing
const startedAt = Date.now()
try {
  const output = await executor({ values, getStagehand })
  step.status = "done"
  step.durationMs = Date.now() - startedAt
  step.output = output
} catch (error) {
  step.status = "failed"
  step.durationMs = Date.now() - startedAt
  step.error = error instanceof Error ? error.message : String(error)
  metadata.set("steps", steps)
  await metadata.flush()
  throw error
}
```

### Why `metadata.flush()` is Critical:
Trigger.dev buffers metadata updates to minimize network requests. Because step executions (especially `open-url` or `act`) can take multiple seconds, calling `await metadata.flush()` ensures that the canvas UI immediately displays the spinner on the running node without waiting for the next background batch.

## 4. Real-Time Telemetry & Scoped Client Streaming

The client monitors running workflows in real-time without polling or custom WebSocket infrastructure.

### Scoped Public Tokens

When loading the workflow page (`app/(dashboard)/workflows/[id]/page.tsx`), the server creates a scoped, short-lived public access token:

```typescript
const runsToken = await triggerAuth.createPublicToken({
  scopes: {
    read: {
      tags: [`workflow:${id}`],
    },
  },
  expirationTime: "1hr",
})
```

### Client Subscription (`features/workflows/components/workflow-runs-provider.tsx`)

The client consumes this token using `@trigger.dev/react-hooks`:

```typescript
export function WorkflowRunsProvider({ workflowId, accessToken, children }) {
  const { runs, error } = useRealtimeRunsWithTag<typeof runWorkflowTask>(
    `workflow:${workflowId}`,
    { accessToken }
  )
  // Provides runs to Canvas nodes, ConsolePanel, and Inspector
}
```

- **Tag Isolation**: The client can only read runs explicitly tagged with `workflow:${workflowId}`.
- **Auto-Resolution**: If a run is still live (`QUEUED` or `EXECUTING`), the UI reads from `run.metadata.steps`. Once the run finishes, it falls back to `run.output.steps`.

## 5. Browserbase Session Replay Pipeline

Browserbase records video of all headless browser interactions. However, recordings require processing after session closure before being playable.

### The 202 Polling Protocol (`app/api/replays/[sessionId]/route.ts`)

1. The frontend requests the recording: `GET /api/replays/[sessionId]`
2. If Browserbase is still encoding the video:
   - Returns **`202 Accepted`** with an empty body.
   - The `<SessionReplay />` component waits 2000ms (`POLL_INTERVAL_MS`) and polls again.
3. Once ready:
   - The route retrieves the `.m3u8` playlist using `browserbase.sessions.replays.retrievePage(...)`.
   - Returns **`200 OK`** with `Content-Type: application/vnd.apple.mpegurl`.
   - The client feeds the URL to **`hls.js`** to stream the recorded cloud session directly inside the canvas console.
